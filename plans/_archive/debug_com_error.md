# Диагностика ошибки COM-автоматизации Excel (v1.0.4)

Дата: 2026-08-21
Статус: **УСТРАНЕНО** (исправление применено и проверено 2026-08-21)

## Исходная ошибка

`scripts/impVBA.py`, строка `excel.Visible = False`:

```
pywintypes.com_error: (-2147352567, 'Ошибка.', (0, None, None, None, 0, -2146777998), None)
```

- Внешний HRESULT: `0x80020009` = **DISP_E_EXCEPTION** (исключение возбуждено самим COM-объектом Excel).
- Внутренний scode: `0x800AC472`.

Также ранее `scripts/run_tests.py` зависал на COM-операциях.

## Выполненные шаги диагностики

### 1. Контекст среды
- Python 3.13.15, pywin32 **312**, venv `.venv` (активен).
- Excel 16.0 (Office16, 2016/365), CLSID `{00024500-0000-0000-C000-000000000046}`.
- Реестр: `HKCU/HKCR\Excel.Application` → `LocalServer32 = C:\Program Files\Microsoft Office\Root\Office16\EXCEL.EXE /automation` — **регистрация COM-сервера корректна**.

### 2. Проверка процессов EXCEL
- `Get-Process EXCEL` — **процессов не обнаружено** на момент диагностики.
- Ранее зависший `run_tests.py` в Terminal 1 **завершился** в 18:42 (запись в `logs/test_results.log`). Зависших python/EXCEL процессов нет.

### 3. Проба COM-инициализации (все три способа)
Тестировались `Dispatch`, `dynamic.Dispatch`, `DispatchEx`, а также `gencache.EnsureDispatch`:

| Способ | Создание | `Visible=False` | `DisplayAlerts=False` | Version |
|---|---|---|---|---|
| `Dispatch` | OK | OK | OK | 16.0 |
| `dynamic.Dispatch` | OK | OK | OK | 16.0 |
| `DispatchEx` | OK | OK | OK | 16.0 |
| `gencache.EnsureDispatch` | OK | OK | OK | 16.0 |

**Все способы работают корректно в текущей сессии.** Кэш `gen_py` существует (`C:\Users\User\AppData\Local\Temp\gen_py\3.13`) и корректно переиспользуется.

### 4. Сверка `impVBA.py` с копией
`fc /N scripts\impVBA.py F:\MiTyA\PROject\copy\SysW\scripts\impVBA.py`
→ **«Различий не найдено»**. Файлы полностью идентичны. Значит текущий `impVBA.py` НЕ является проблемной версией — регрессия в зоне COM отсутствует.

## Перечень рассмотренных причин (>=5)

| # | Причина | Результат проверки | Вывод |
|---|---|---|---|
| 1 | Отключённая/повреждённая автоматизация Excel (DisableExcelAuto, DDE) | Реестр корректен, COM создаётся | ❌ исключена |
| 2 | Конфликт версий Office/Excel | Excel 16.0 зарегистрирован, версия читается | ❌ исключена |
| 3 | Недостаточные права процесса | Объект создаётся и управляется | ❌ исключена |
| 4 | Несовместимость режима запуска (фоновая/интерактивная сессия) | В текущей интерактивной сессии работает | ❌ исключена (для данного запуска) |
| 5 | Проблема инициализации COM-объекта (gencache/gen_py) | `gen_py` валиден, early+late binding работают | ❌ исключена |
| 6 | Влияние сторонних надстроек Excel | Не тестировалось в полном объёме | ⚠️ требует проверки |

| 8 | **Конфликт с уже запущенным/зависшим EXCEL.EXE** | Исторически был зависший `run_tests.py`, который удерживал экземпляр Excel | ✅ **наиболее вероятная** |

## Вероятная корневая причина

Основной фактор: механизм `win32com.client.Dispatch("Excel.Application")` / `EnsureDispatch`
при наличии уже запущенного (скрытого, «зомби») экземпляра Excel **подключается к существующему процессу**,
а не создаёт новый. Если этот экземпляр находится в некорректном состоянии
(завис во время `RunAllTests`, показал модальное диалоговое окно, потерял RPC-канал),
то обращение к свойству `Visible` завершается `DISP_E_EXCEPTION` (scode `0x800AC472`).

Это объясняет оба симптома:
- зависание `run_tests.py` на COM-операции;
- падение `impVBA.py` на `excel.Visible = False`.

На момент текущей диагностики (процессов EXCEL нет) все способы создания COM-объекта работают —
подтверждает ситуативный характер ошибки, а не постоянную поломку автоматизации.

## Предлагаемое решение (требует согласия)

Для надёжности рекомендуется:

1. **Гарантированно завершать фоновые EXCEL.EXE перед COM-операцией** (или использовать
   `win32com.client.DispatchEx("Excel.Application")`, который всегда создаёт НОВЫЙ экземпляр,
   не привязываясь к существующему «зомби»).
2. Добавить в оба скрипта (`impVBA.py`, `run_tests.py`) устойчивое завершение:
   `excel.Quit()` + `excel = None` + сборка мусора (`gc.collect()`) и защиту от зависших процессов.
3. Установить `excel.AutomationSecurity = 3` и `excel.DisplayAlerts = False` ДО открытия книги.

Примечание: это **правки в рабочий вариант** — применяются ТОЛЬКО после явного подтверждения пользователя,
с предварительным созданием резервной копии `scripts/impVBA.py.bak`.

## Применённое исправление (по согласованию, только impVBA.py)

Файл: [`scripts/impVBA.py`](scripts/impVBA.py). Резервная копия: `scripts/impVBA.py.bak`.

1. Основной способ создания COM-объекта заменён на `win32com.client.DispatchEx("Excel.Application")`
   — всегда создаёт НОВЫЙ выделенный экземпляр Excel, не привязываясь к «зомби»-процессу.
   Фолбэки: `Dispatch` → `gencache.EnsureDispatch` → `dynamic.Dispatch`.
2. До открытия книги установлено `excel.AutomationSecurity = 3` (msoAutomationSecurityForceDisable),
   `Visible=False`, `DisplayAlerts=False`.
3. В `finally`: `excel.Quit()` обёрнут в try/except, `excel = None`, добавлен `gc.collect()`.

`run_tests.py` — НЕ изменялся (по указанию пользователя).
