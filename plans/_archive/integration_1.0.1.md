## 1. Анализ текущего состояния (итоги предварительного анализа)

### 1.1 Логгер `Mod_Logger.bas`

Текущий API ([`src/modules/Mod_Logger.bas`](../src/modules/Mod_Logger.bas)):

| Метод | Сигнатура | Назначение |
|-------|-----------|-----------|
| `GetLogPath` | `Function As String` | Путь к `logs/log.txt` |
| `WriteLog` | `Sub (moduleName, message)` | Базовая запись без уровня |
| `WriteLogE` | `Sub (moduleName, message)` | Ошибка с префиксом `[ERROR]` **внутри сообщения** |
| `RotateLogIfNeeded` | `Sub (maxSizeKB)` | Ротация `log.txt` → `log_old.txt` при >100 КБ |
| `ClearLog` | `Sub ()` | Очистка лога |

Текущий формат строки:

```
[ГГГГ-ММ-ДД ЧЧ:ММ:СС] [moduleName] message
```

Проблемы:

1. **Уровней INFO / WARN / DEBUG нет.** Метод `WriteLogE` лишь подставляет `[ERROR]` в текст сообщения, но нигде не вызывается (только определён) — ошибки пишутся обычным `WriteLog` без маркировки уровня.
2. **Три стиля вызова логгера:**
   - прямой `Mod_Logger.WriteLog(module, msg)` — ~**90+ вызовов**;
   - обёртка `Mod_Utils.WriteLog(msg)` — **15 вызовов**, всегда пишет модуль `"Mod_Utils"` и **теряет имя реального вызывающего модуля**;
   - диспетчер `Mod_Utils.WriteLog_UI` — вызывает обёртку `WriteLog` внутри себя.
3. **Рассинхрон имени:** [`Лист2_main.cls`](../src/sheets/Лист2_main.cls:45) передаёт `moduleName="Sheet1_main"` вместо `"Лист2_main"`.
4. **Разнобой в стиле сообщений:** `«функция: текст»`, `«МОДУЛЬ: START/END»`, смешение рус./англ., непоследовательное тире.

### 1.4 Python-окружение («падение» виртуального окружения)

- Виртуальное окружение `.venv` расположено в корне проекта, исключено из git (`.gitignore`) и из Syncthing (`.stignore`).
- **Отсутствует `requirements.txt`** — единственная внешняя зависимость `pywin32` ставится вручную (`pip install pywin32`).
- Главные причины «падения» после переноса/синхронизации:
  1. **Абсолютные пути** в `.venv` (`pyvenv.cfg`, `activate.bat`, скрипты `pip`/`pywin32`) — при переносе окружение перестаёт работать.

  3. Если `.venv` не создан — VS Code подхватывает системный Python, `activate.bat` не срабатывает, импорт `win32com` падает.

## 2. Целевая схема логгера (предлагаемый дизайн)

### 2.1 Уровни логирования

Вводим 4 уровня (перечисление для использования в коде и документации):

| Уровень | Назначение |
|---------|-----------|
| `INFO`  | Информационные сообщения, старт/конец операций, ключевые значения |
| `WARN`  | Предупреждения (не критичные, но требующие внимания) |
| `ERROR` | Ошибки (в блоках `ErrHandler` и при сбоях) |
| `DEBUG` | Отладочные детали (значения переменных, промежуточные вычисления) |

### 2.2 Целевой формат строки лога

```
[ГГГГ-ММ-ДД ЧЧ:ММ:СС] [УРОВЕНЬ] [Модуль] сообщение
```

Пример:

```
[2026-08-06 18:40:00] [INFO] [Mod_AutoMatch] AutoMatchWorks: START
[2026-08-06 18:40:01] [ERROR] [Mod_AutoMatch] AutoMatchWorks: Ошибка — деление на ноль
```

### 2.3 Предлагаемые сигнатуры (вариант на согласование)

**Вариант A — единый метод с параметром уровня (рекомендуется, соответствует R-07):**

```vba
Public Enum LogLevel
    INFO = 0
    WARN = 1
    ERROR = 2
    DEBUG = 3
End Enum

Public Sub WriteLog(ByVal moduleName As String, ByVal message As String, _
                    Optional ByVal level As LogLevel = INFO)
```

- Обратная совместимость: старые вызовы `WriteLog(module, msg)` остаются валидными (уровень по умолчанию `INFO`).
- `WriteLogE` остаётся как обёртка над `WriteLog(module, msg, ERROR)` — но теперь с корректным уровнем.

**Вариант B — отдельные методы:**

```vba
Public Sub WriteLog(ByVal moduleName As String, ByVal message As String)   ' INFO
Public Sub WriteLogE(ByVal moduleName As String, ByVal message As String)  ' ERROR
Public Sub WriteLogW(ByVal moduleName As String, ByVal message As String)  ' WARN
Public Sub WriteLogD(ByVal moduleName As String, ByVal message As String)  ' DEBUG
```

**Рекомендация:** Вариант A (единый `WriteLog` + `Enum LogLevel`) — он соответствует уже заложенному в ROADMAP R-07 (`WriteLog(Message, Level)`), минимизирует правки (старые вызовы валидны) и позволяет точечно повышать/понижать уровень.

Дополнительно предлагается:

- Добавить `Public Const LOG_LEVEL` / фильтр минимального уровня записи (например, `SetMinLevel(level)`), чтобы отключать `DEBUG` в продакшене.
- Сохранить `GetLogPath()`, `RotateLogIfNeeded()`, `ClearLog()` без изменений сигнатур.

### 2.4 Решение проблемы обёртки `Mod_Utils.WriteLog`

**Рекомендация:** полностью отказаться от обёртки `Mod_Utils.WriteLog(msg)` и заменить все её внешние вызовы на прямой `Mod_Logger.WriteLog(реальный_модуль, msg, level)`.

- Внешние вызовы (15 шт.) в `Mod_SheetOps`, `Mod_Import`, `Mod_OrderHeader`, `Mod_FullTestRunner` заменить на прямой вызов с фактическим именем модуля и подходящим уровнем (ошибки → `ERROR`, информационные → `INFO`).
- Внутренние вызовы в `Mod_Utils` (`WriteLog_UI`, `ShowWorkbookPath_UI`, `ShowCurrentUser_UI`, `CheckFileExists_UI`) заменить на `Mod_Logger.WriteLog("Mod_Utils", ...)`.
- Сама обёртка `Mod_Utils.WriteLog` помечается как устаревшая (`@Deprecated` в комментарии) и/или удаляется после замены всех вызовов. **Решение о полном удалении или оставлении заглушки — на согласование (см. раздел 8).**
- `WriteLog_UI` и диспетчер `Btn_main_WriteLog_Click` (в `Mod_ButtonDispatcher`) сохраняют функциональность, но используют новый API.

### 2.5 Решение проблемы рассинхрона имени `Лист2_main.cls`

- В [`Лист2_main.cls:45`](../src/sheets/Лист2_main.cls:45) заменить `moduleName="Sheet1_main"` на `"Лист2_main"` (фактическое имя компонента по `Attribute VB_Name = "Лист2"`, файл `src/sheets/Лист2_main.cls`).
- Единообразно передавать в логгер именно код VB-компонента (имя модуля), а не имя листа.

### 2.6 Систематизация стиля сообщений

Унифицировать стиль сообщений (применимо к правкам в рамках этой задачи):

- Формат: `ИмяПроцедуры: текст`.
- Сообщения — на русском (значения/идентификаторы — как есть).
- Признак старта/конца: `Процедура: START` / `Процедура: END`.
- Ошибки в `ErrHandler`: `Процедура: Ошибка — <описание>` на уровне `ERROR`.

> **Ограничение:** полная переработка всех ~90+ сообщений — отдельная объёмная задача. В рамках v1.0.1 предлагается систематизировать **формат и уровни** (добавить уровни к существующим вызовам), не переписывая тексты всех сообщений. Тексты на рус. и `START/END` унифицируются точечно в местах правок.

### 3.3 Воспроизводимая настройка окружения (процедура)

Предлагаемая документированная процедура (Windows):

```powershell
# 1. Создание окружения
python -m venv .venv

# 2. Активация
.\.venv\Scripts\Activate.ps1

# 3. Установка зависимостей из фиксации
pip install -r requirements.txt

# 4. Проверка
python -c "import win32com.client; print('OK')"
```

### 3.4 Способ избежать «падения» из-за абсолютных путей

Рекомендуемая стратегия — **не хранить и не переносить `.venv`** (он уже исключён из git и `.stignore`):

1. **Пересоздание окружения** при переносе/синхронизации: удалить `.venv` и выполнить процедуру из п. 3.3 (теперь это быстро и воспроизводимо, т.к. есть `requirements.txt`).
2. **(Опционально)** Скрипт `scripts/setup_venv.ps1`, который проверяет наличие `.venv` и корректность (наличие `win32com`), а при отсутствии/некорректности — пересоздаёт его по `requirements.txt`. Это исключает ручные действия и зависимость от абсолютных путей.
3. **Не коммитить** `.venv` (уже в `.gitignore` / `.stignore` — подтвердить).

> ВАЖНО: сам `.venv` в git не попадает и в коммит не включается. Правка файлов самого `.venv` в рамках этой задачи не выполняется — вместо этого фиксируются зависимости и процедура пересоздания.

## 5. Кодировка и способ внесения правок ([K1]/[K2], [S4])

- Репозиторий хранит исходники в **UTF-8**; VBA-редактор Excel работает в **CP1251**.
- VBA-модули меняются **только** через скрипты:
  1. `python scripts/impVBA.py` — импорт из `src/` в `work.xlsm` (UTF-8 → CP1251);
  2. `python scripts/export_vba.py` — экспорт из `work.xlsm` в `src/` (CP1251 → UTF-8).
- Правки `.bas`/`.cls` вносятся в исходники `src/`, затем импортируются; либо экспортируются из Excel, правятся, импортируются обратно. Финальные версии в `src/` должны быть в UTF-8 без BOM.
- Комментарии — на русском ([G9]).

## 6. Риски

| Риск | Митигация |
|------|-----------|
| Смена сигнатуры `WriteLog` сломает обратную совместимость | Уровень по умолчанию `INFO`; старые вызовы с 2 аргументами остаются валидными |
| Полное удаление `Mod_Utils.WriteLog` может затронуть внешний код | Все внешние вызовы (15) заменяются заранее; решение об удалении — на согласование |
| Пересоздание `.venv` на удалённом устройстве без `requirements.txt` | Фиксация зависимостей в `requirements.txt`; документированная процедура |
| Правка критических файлов (`CHANGELOG.md`, `README.md`) | Правка только по явной команде ([E3]) |
| Массовая замена ~90 вызовов логгера | Точечная простановка уровней по матрице; тексты сообщений не переписываются массово |
