# План исправления ошибок синхронизации проекта через Syncthing

> **Статус:** черновик (Architect)
> **Цель:** устранить ошибки синхронизации проекта `SysW` между устройствами в домашней локальной сети, в т.ч. «пропадание загрузки виртуального окружения Python».
> **Приоритет правил:** `.ycarules` (высший приоритет) — учтены `[S7]`, `[E1]`, `[E3]`, `[Z2]`.

---

## 1. Диагноз (кратко)

Syncthing использует **собственный** файл исключений `.stignore` (в корне синхронизируемой папки) и **НЕ читает** `.gitignore`, `.sourcecraft`, `.vscode/settings.json`. Поэтому все исключения, настроенные для Git/VS Code/SourceCraft, не действуют при синхронизации.

Файлы/папки, нарушающие целостность проекта при синхронизации:

| Объект | Причина проблемы | Где уже исключён (но Syncthing не читает) |
|--------|------------------|-------------------------------------------|
| `.venv/`, `venv/` | Абсолютные пути в `pyvenv.cfg`, `Scripts/activate.bat` различаются между устройствами → ломается окружение | `.gitignore`, `.sourcecraft` |
| `_backup/` | 8 бинарных `.xlsm`/`.xlsx` копий → конфликты синхронизации | нигде |
| `workOt/` | `*.xlsm`, `*.xlsx`, `calc/*.xml` синхронизируются | `.sourcecraft`, `.vscode/settings.json` (не `.gitignore`) |
| `src/sheets/*.bak` | `.bak`-копии не исключены нигде | нигде |
| `~$*.xls*` | Блокировки Excel при открытой книге | `.gitignore` (не `.sourcecraft`) |
| `__pycache__/`, `*.pyc`, `*.pyo` | Мусор Python | `.gitignore`, `.sourcecraft` |
| `_temp_export/`, `_temp_import/` | Временные данные | `.gitignore`, `.sourcecraft` |
| `*.log`, `*.tmp` | Логи/временные файлы | `.gitignore`, `.sourcecraft` |
| `*.sync-conflict-*` | Конфликтные копии Syncthing | `.sourcecraft` |
| `Thumbs.db`, `Desktop.ini`, `.DS_Store` | Системный мусор | `.sourcecraft`, `.vscode` |

## 2. Задача 1.1 — Рассмотренные варианты

### Вариант A. Исключение всей папки проекта из синхронизации
- **Суть:** не синхронизировать `SysW` целиком.
- **Плюсы:** полное отсутствие конфликтов.
- **Минусы:** проект перестаёт синхронизироваться между устройствами — противоречит цели задачи. **Отклонено.**

### Вариант B. Исключение отдельных файлов/папок, нарушающих целостность (РЕКОМЕНДУЕТСЯ)
- **Суть:** создать/дополнить `.stignore` в корне проекта с правилами исключения проблемных объектов.
- **Плюсы:** проект синхронизируется, исключается только «мусор» и окружение; решение хранится в самом проекте и автоматически распространяется на все устройства.
- **Минусы:** требует ручного сопровождения списка исключений.
- **Вывод:** основной рекомендуемый вариант.

### Вариант C. Настройка через файл конфигурации внутри проекта или Syncthing ConfigurationPage
- **Суть:** управлять исключениями через GUI Syncthing (Web UI) или через `~/.config/syncthing/`.
- **Плюсы:** не требует файла в проекте.
- **Минусы:** настройка привязана к конкретному устройству, не распространяется автоматически; легко потерять при переустановке. Используется как **дополнение** к варианту B.

## 3. Задача 1.2 — Дополнительные варианты синхронизации

1. **`.stignore` в корне проекта** — основной механизм Syncthing (см. раздел 4).
2. **Настройка через Syncthing ConfigurationPage (GUI)** — добавить те же паттерны в поле «Ignore Patterns» для папки `SysW` (Web UI → папка → «Игнорирование»). Дублирует `.stignore`, но полезно как резерв.
3. **Игнорирование на уровне папки через `~/.config/syncthing/`** — правка `config.xml` (секция `<folder>` → `<ignorePatterns>`). Только для продвинутых, рискованно.
4. **Не синхронизировать `.venv` вообще** — создавать виртуальное окружение отдельно на каждом устройстве (рекомендуется как лучшая практика). `.venv` исключается из синхронизации, а на каждом устройстве выполняется `python -m venv .venv` + `pip install -r requirements.txt`.
5. **Синхронизация только исходников, а не бинарных книг** — `work.xlsm`, `report.xlsx`, `base/models/*.xlsm` — бинарные и конфликтуют. Вариант: синхронизировать только `src/`, `scripts/`, `docs/`, `plans/`, а бинарные книги распространять вручную/через git LFS. **Требует согласования** (критические файлы `[E3]`).
6. **Использование git как основного канала синхронизации** — Syncthing для рабочих файлов, git для кода. Дополнительный, не заменяет Syncthing.

## 4. Рекомендуемый вариант: `.stignore`

### 4.1 Обоснование
- `.stignore` — единственный файл, который Syncthing читает для исключений.
- Размещение в корне проекта позволяет автоматически распространять правила на все устройства (файл синхронизируется сам).
- Не требует ручной настройки GUI на каждом устройстве.

### 4.2 Полное содержимое предлагаемого `.stignore`

```text
// Файл исключений Syncthing для проекта SysW
// Синтаксис: glob-паттерны, (?i) — регистронезависимость, ! — исключение из исключения
// См. https://docs.syncthing.net/users/ignoring.html

// --- Виртуальное окружение Python (абсолютные пути ломают окружение) ---
(?i).venv/
(?i)venv/

// --- Кэш и мусор Python ---
(?i)__pycache__/
(?i)*.pyc
(?i)*.pyo

// --- Временные директории скриптов ---
_temp_export/
_temp_import/

// --- Резервные копии (бинарные .xlsm/.xlsx) ---
_backup/

// --- Рабочая папка (не синхронизируется) ---
workOt/

// --- Резервные копии VBA-классов ---
src/sheets/*.bak

// --- Блокировки Excel при открытой книге ---
(?i)~$*
(?i)*.tmp

// --- Логи ---
(?i)*.log

// --- Конфликтные копии Syncthing ---
*.sync-conflict-*

// --- Системный мусор ---
(?i)Thumbs.db
(?i)Desktop.ini
.DS_Store

// --- node_modules (если появится) ---
node_modules/
```

### 4.3 Пояснения к синтаксису
- `(?i)` — регистронезависимое совпадение (для Windows-путей, где регистр не важен).
- Паттерн с завершающим `/` исключает **всю папку** рекурсивно.
- `!` (не используется здесь) — «исключение из исключения», позволяет вернуть файл внутри исключённой папки. Пример: `!workOt/keep_me.xlsm`.
- Паттерны применяются относительно корня синхронизируемой папки.
- Комментарии начинаются с `//`.

## 5. Решение: коммитить ли `.stignore` в git?

**Рекомендация: ДА, закоммитить `.stignore` в git.**

### Обоснование
1. **Распространение на все устройства.** Если `.stignore` закоммичен, он попадает на все устройства через git (или через саму синхронизацию Syncthing). Это гарантирует единообразие правил исключений.
2. **История изменений.** Правила исключений — часть конфигурации проекта; их изменения должны отслеживаться (см. `[U2]` CHANGELOG).
3. **Не является секретом.** `.stignore` не содержит чувствительных данных.
4. **Риск минимален.** Файл небольшой, текстовый, не влияет на работу Git/VS Code/SourceCraft.

### Важное замечание
- `.stignore` **не должен** попадать в `.gitignore` (иначе он не будет распространяться через git).
- НО: если `.stignore` синхронизируется через Syncthing, он сам будет распространяться между устройствами. Это **желательно** — правила будут одинаковыми везде.
- **Нюанс:** если `.stignore` синхронизируется через Syncthing, изменения на одном устройстве автоматически попадут на другие. Это плюс, но требует осторожности при редактировании (конфликты маловероятны, т.к. файл текстовый).

## 6. Пошаговый план реализации

> **Внимание:** режим Architect не вносит изменения в код/конфиги. Ниже — план для режима Code. Критические файлы (`[E3]`) не изменяются без согласования.

### Шаг 1. Создать `.stignore` в корне проекта
- Создать файл `l:/PROject/SysW/.stignore` с содержимым из раздела 4.2.
- Файл текстовый, кодировка UTF-8 (без BOM), окончания строк LF (согласуется с `.gitattributes`).

### Шаг 2. Проверить, что `.stignore` не конфликтует с `.gitignore`
- Убедиться, что `.stignore` **не** добавлен в `.gitignore` (иначе не будет распространяться через git).
- При необходимости добавить `.stignore` в `.sourcecraft` как `Include` (чтобы ассистент учитывал его при анализе) — **по согласованию**.

### Шаг 3. Синхронизировать `.stignore` на все устройства
- Через Syncthing (файл появится на других устройствах автоматически) **или** через git (после коммита и пуша).
- На каждом устройстве Syncthing применит правила исключений.

### Шаг 4. Удалить уже синхронизированный «мусор» (по согласованию, `[Z2]`)
- После применения `.stignore` Syncthing **не удаляет** уже синхронизированные файлы автоматически (только перестаёт их синхронизировать).
- Для очистки: в Syncthing Web UI → папка → «Игнорирование» → кнопка «Удалить игнорируемые файлы» (или вручную удалить `.venv`, `_backup`, `workOt`, `__pycache__`, `*.bak`, `~$*` на устройствах).
- **Запрос у пользователя перед удалением** (правило `[Z2]`).

### Шаг 5. Восстановить виртуальное окружение на каждом устройстве
- `.venv` исключён из синхронизации → на каждом устройстве создать заново:
  - `python -m venv .venv`
  - `.venv\Scripts\activate.bat`
  - `pip install -r requirements.txt` (если есть `requirements.txt`; при отсутствии — установить зависимости вручную).
- Обновить `python.defaultInterpreterPath` в `.vscode/settings.json` при необходимости (путь уже указан как `${workspaceFolder}/.venv/Scripts/python.exe` — корректен).

### Шаг 6. Обновить документацию
- Обновить `CHANGELOG.md` (`[U2]`).
- При необходимости дополнить `docs/DEVELOPER.md` разделом о синхронизации.

### Шаг 7. Коммит и пуш (по запросу пользователя)
- После завершения всех задач — запросить у пользователя разрешение на коммит и пуш (согласно `plans/promt.md`).

## 7. План проверки

### 7.1 Проверка синхронизации
1. На устройстве A создать/изменить тестовый файл в `src/` (например, `src/modules/Mod_Utils.bas`).
2. Дождаться синхронизации (Syncthing Web UI → статус папки «Up to Date»).
3. На устройстве B убедиться, что файл обновился.
4. Убедиться, что `.venv/`, `_backup/`, `workOt/`, `__pycache__/`, `*.bak`, `~$*` **не** синхронизируются (не появляются на устройстве B).
5. Проверить, что `.stignore` синхронизировался на устройство B.

### 7.2 Проверка виртуального окружения
1. На каждом устройстве активировать окружение: `.venv\Scripts\activate.bat`.
2. Проверить, что `python --version` и `pip --version` работают.
3. Запустить тесты: `python scripts/run_tests.py` (или `python -m pytest`).
4. Убедиться, что пути в `pyvenv.cfg` указывают на локальное устройство (не на удалённое).

### 7.3 Проверка чистоты проекта (`[S7]`)
- Убедиться, что в проекте нет `__pycache__`, `*.sync-conflict-*`, `~$*.xlsm`, временных файлов.
- Проверить, что `_temp_export/`, `_temp_import/` пусты или отсутствуют.

---

## 8. Риски и ограничения

- **`.stignore` не удаляет уже синхронизированные файлы** — требуется ручная очистка (Шаг 4).
- **`.venv` на каждом устройстве** — окружение создаётся локально; зависимости должны быть воспроизводимы (рекомендуется `requirements.txt`).
- **Бинарные книги** (`work.xlsm`, `report.xlsx`, `base/models/*.xlsm`) — при одновременном редактировании на двух устройствах возможны конфликты. Рекомендуется редактировать на одном устройстве за раз.
- **Критические файлы** (`[E3]`) — не изменяются без явного согласования.

---

## 9. Итог

Рекомендуемый вариант — **создать `.stignore` в корне проекта** с правилами исключения проблемных объектов (раздел 4.2) и **закоммитить его в git** для распространения на все устройства. Дополнительно — настроить те же паттерны через Syncthing ConfigurationPage как резерв и создать `.venv` локально на каждом устройстве.
