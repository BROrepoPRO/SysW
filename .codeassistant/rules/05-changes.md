# Управление изменениями — рабочие правила [U]

> Зеркало модуля «Управление изменениями» из `.ycarules`. Коды правил идентичны.

## [U1] РЕГИСТРАЦИЯ ЗАДАЧ В TODO (вместо обязательного плана)

**Глобальное поведение агентов (v1.1.0):** при поступлении промта/подзадачи **вместо создания
плана на промт** необходимо **зарегистрировать задачу в todo** (todo-список, ROADMAP §11).
1. Зарегистрировать задачу/подзадачу в todo.
2. При необходимости (для сложных или архитектурных изменений) – создать план в `plans/`
   (Markdown) и согласовать с пользователем.
3. После утверждения – внести изменения.
4. После исполнения – отметить задачу выполненной; план при наличии переместить в `plans/_archive/`.
**Примечание:** обязательное создание плана отменено; `plans/` используется по решению
Orchestrator для крупных/архитектурных задач.

## [U2] CHANGELOG И ВЕРСИОНИРОВАНИЕ

При любых изменениях, влияющих на функциональность – обновить `docs/CHANGELOG.md`
(формат Keep a Changelog). Версия проекта: `X.Y.Z` (SemVer) или расширенная `X.Y.Z.W`
(v1.1.0): компонента **W** инкрементируется при изменениях внутри одного промта
(todo/CHANGELOG/commits), например `1.0.18.1`. Обновление версии — через
`scripts/update_version.py`.

## [U3] ТОЧНОСТЬ ВЫПОЛНЕНИЯ

Строго следовать инструкциям, не отклоняться и не добавлять незапрошенный функционал.
При неоднозначности – уточнить у пользователя.

## [U4] ЕДИНЫЙ ЗАПРОС НА КРИТИЧЕСКИЕ ФАЙЛЫ ПОДЗАДАЧИ

Если выполнение подзадачи требует изменения нескольких критических файлов (см. `[E3]`) –
запрос на изменение следует провести **один раз для всех файлов подзадачи**, одной точкой
подтверждения (а не поочерёдно на каждый файл). Перечислять все целевые файлы и планируемые правки одним блоком необязательно. Пример: групповая комбинация git-команд (add/commit/push),
покрывающая все файлы подзадачи за один вызов.
**Последовательности команд (v1.1.0, Задача 6):** выполнение цепочки команд Python/PowerShell
(`python ...`, `pwsh -Command ...`) также объединяется в единый запрос/одну точку подтверждения
до запуска; целевые команды и их назначение указывать одним блоком необязательно.

## [U5] КОПИЯ ПЕРЕД ИЗМЕНЕНИЕМ КЛЮЧЕВЫХ ФАЙЛОВ EXCEL

Перед изменением **любого ключевого файла Excel** (`work.xlsm`, `report.xlsx`, шаблоны
`base/templates/*`, модельные книги `base/models/*`) – **всегда создавать резервную копию изменяемого файла, но не всей системы**
до начала правок этого файла. Копия создаётся автоматически (этап 1 `scripts/build_all.py`, точка отката
`_backup/<stamp>/`) либо вручную перед ручным редактированием. Правило действует независимо
от того, кто редактирует файл – ассистент или пользователь. Перечень защищённых файлов
централизован (константа `PROTECTED_FILES` в `scripts/config.py`, см. `[E3]`).

## [U6] МОНИТОРИНГ ДЛИТЕЛЬНЫХ ПРОЦЕССОВ

При выполнении длительных процессов (COM-сборка, тесты, форматирование шаблонов и т.п.) –
**запускать фоновый мониторинг** через `scripts/monitor_long.ps1` (опрашивает процессы
каждые N секунд, пишет статус в закреплённый лог-файл `logs/monitor_long.log` или кастомный).
Это позволяет отслеживать прогресс и момент завершения, не перегружая контекст ИИ.

## [U7] СИНХРОНИЗАЦИЯ TODO ↔ CHANGELOG ↔ COMMITS (единая версия)

(v1.1.0, Задача 4) Обеспечить согласованность между todo, `docs/CHANGELOG.md` и git-коммитами:
1. Каждая задача, зарегистрированная в todo, должна находить отражение в `docs/CHANGELOG.md`
   (запись в разделе соответствующей версии) и в коммите с той же версией/областью.
2. Коммиты — по Conventional Commits с областью, соответствующей номеру версии/задачи.
3. При изменении версии проекта обновляются **взаимно связанные** точки: todo (ROADMAP §11),
   `docs/CHANGELOG.md`, `docs/DEVELOPER.md`, `docs/ROADMAP.md`, `config.py`, `Mod_Constants`,
   `README.md` — одной версией (X.Y.Z или X.Y.Z.W).
4. Проверять отсутствие расхождений между ссылками (перекрёстные ссылки на реестр/версию).
